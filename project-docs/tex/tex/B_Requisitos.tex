\apendice{Especificación de requisitos}

\section{Introducción}
Dentro de este apéndice, se detalla la especificación de requisitos del proyecto del laboratorio virtual de programación y robótica. Una adecuada definición y gestión de los requisitos es fundamental en ingeniería de software para asegurar que el sistema desarrollado satisfaga las necesidades y expectativas de los usuarios, así como para guiar las fases posteriores de diseño e implementación. Dada la naturaleza de prototipo del presente Trabajo Fin de Grado, esta especificación se centrará en los requisitos que guían la funcionalidad actual del prototipo, así como aquellos objetivos clave que sentarán las bases para futuras expansiones. Los requisitos se clasifican en funcionales (qué debe hacer el sistema) y no funcionales (cómo debe funcionar, relativo a la calidad).

\section{Objetivos generales del proyecto}
Los objetivos generales que guían el desarrollo de este laboratorio virtual han sido definidos previamente en el Capítulo 2 de la memoria. Estos objetivos, que se persiguen tanto a nivel funcional como no funcional, se sintetizan a continuación:

\begin{itemize}
	\item Desarrollar una plataforma educativa que ofrezca \textbf{dos itinerarios de programación paralelos}: uno visual por bloques y otro textual mediante un DSL.
	\item Implementar un sistema funcional de \textbf{programación por bloques} para la estructura del programa, inspirado en la interacción de Scratch.
	\item Diseñar y construir un \textbf{intérprete completo para un DSL textual propio}, incluyendo su parser y motor de ejecución.
	\item Integrar ambos sistemas de programación con un \textbf{motor de simulación 3D unificado} y con detección de colisiones.
	\item Estructurar el aprendizaje en un \textbf{sistema de desafíos} modular y escalable.
	\item Garantizar la \textbf{accesibilidad y portabilidad} del prototipo, con un enfoque en dispositivos Android.
\end{itemize}

\section{Catálogo de requisitos}
El siguiente catálogo enumera los requisitos clave del prototipo. Se organizan por tipo y se proporciona un identificador único (RF para Requisito Funcional, RNF para Requisito No Funcional) y una descripción concisa del mismo.

\subsection{Requisitos funcionales (RF)}
Estos requisitos describen las funcionalidades específicas que el laboratorio virtual debe proporcionar al usuario.

\subsection{Gestión del entorno y desafíos}

\begin{enumerate}
  \item[\textbf{RF-001}] \textbf{Selección de desafíos:} El sistema debe ofrecer una interfaz para que el usuario seleccione un desafío de aprendizaje.
	\item[\textbf{RF-002}] \textbf{Carga de contexto:} Al elegir un desafío, el entorno debe cargarse mostrando las instrucciones y configuración específicas de dicho desafío.
	\item[\textbf{RF-003}] \textbf{Selección de modalidad de programación:} La interfaz debe permitir al usuario elegir entre el itinerario de programación por bloques o el itinerario textual.

	\item[\textbf{RF-004}] \textbf{Manipulación de bloques:} El usuario debe poder arrastrar bloques desde una toolbox, soltarlos en un área de trabajo, y conectarlos/desconectarlos para formar secuencias lógicas.
	\item[\textbf{RF-005}] \textbf{Librería de bloques estructurales:} El sistema debe proveer bloques funcionales para el evento de inicio y para estructuras de control básicas (ej. bucles).
	\item[\textbf{RF-006}] \textbf{Eliminación de bloques:} El usuario debe poder eliminar bloques del área de trabajo.
	
	 \item[\textbf{RF-007}] \textbf{Entrada de comandos:} El sistema debe proporcionar una interfaz para que el usuario escriba comandos del DSL.
	\item[\textbf{RF-008}] \textbf{Validación sintáctica (Parsing):} El sistema debe analizar el código textual y notificar al usuario de cualquier error de sintaxis.
	\item[\textbf{RF-009}] \textbf{Visualización del programa textual:} Los comandos válidos deben representarse visualmente como una lista secuencial.
	 \item[\textbf{RF-010}] \textbf{Ejecución unificada:} El usuario debe poder iniciar la ejecución del programa, independientemente del modo, con una única acción.
	\item[\textbf{RF-011}] \textbf{Interpretación de instrucciones:} El motor de ejecución debe interpretar el programa (ya sea el árbol de bloques o la lista de instrucciones del DSL) y traducirlo a acciones del robot.
	\item[\textbf{RF-012}] \textbf{Simulación 3D del robot:} El robot virtual debe moverse y rotar en el entorno 3D según las instrucciones.
	\item[\textbf{RF-013}] \textbf{Detección de colisiones:} La ejecución debe detenerse automáticamente si el robot colisiona con un obstáculo.

\end{enumerate}



\subsection{Requisitos no funcionales (RNF)}
Estos requisitos describen las cualidades del sistema que garantizan un buen funcionamiento y una experiencia de usuario óptima.
\begin{enumerate}
	\item \textbf{RNF-001: Rendimiento de la interfaz.} La interfaz de programación visual debe responder a las interacciones del usuario (arrastre, conexión) con una latencia mínima, garantizando una experiencia fluida.
	\\
	\item \textbf{RNF-002: Consistencia visual.} El diseño visual de los bloques y la interfaz debe ser consistente con la estética de Scratch. 
	\\
	\item \textbf{RNF-003: Accesibilidad.} El sistema debe ser capaz de ejecutarse en dispositivos Android tipo tablet con hardware común, sin requerimientos técnicos elevados. 
	\\
	\item \textbf{RNF-004: Precisión de la simulación.} El movimiento y el comportamiento del robot simulado deben ser perceptibles y acordes con la lógica programada en los bloques. 
	\\
	\item \textbf{RNF-005: Mantenibilidad.} La arquitectura del software debe facilitar la futura modificación y extensión del sistema de bloques y la lógica del robot.
	\\
	\item \textbf{RNF-006: Confiabilidad.} El sistema no debe experimentar caídas o bloqueos inesperados durante la interacción normal o la ejecución de programas.
	\\
	\item \textbf{RNF-007: Modularidad del código.}
	La arquitectura del software del sistema debe estar organizada siguiendo el patrón Modelo-Vista-Controlador (MVC), promoviendo una clara separación de responsabilidades. Los componentes dentro de cada capa (Modelo, Vista y Controlador) deben diseñarse con principios de \textit{bajo acoplamiento} (interdependencia mínima entre módulos) y \textit{alta cohesión} (elementos dentro de un módulo con funcionalidades estrechamente relacionadas). Esta estructura facilitará la comprensión del código, la depuración, la modificación aislada de componentes y el mantenimiento general del sistema.
	\\	
	\item \textbf{RNF-008: Extensibilidad para nuevos bloques.}
	El diseño del sistema debe permitir la adición de nuevos tipos de bloques de programación con un impacto mínimo y localizado en el código fuente existente. La incorporación de un nuevo bloque debería, idealmente, implicar la creación de:
	\begin{itemize}
		\item Una definición de bloque.
		\item Una clase para su modelo lógico .
		\item Un prefab para su representación visual en Unity UI .
		\item Una clase intérprete  si el bloque es ejecutable.
	\end{itemize}
	Estos nuevos componentes deben poder integrarse sin requerir modificaciones extensas en el núcleo del sistema o los controladores principales.
	\\
	\item \textbf{RNF-009: Usabilidad y retroalimentación visual clara.}
	El sistema debe proporcionar indicaciones visuales claras e intuitivas al usuario durante las interacciones clave para facilitar su uso y comprensión:
	\begin{itemize}
		\item \textbf{Resaltado de conexiones válidas:} Durante la operación de arrastre de un bloque, las posibles conexiones compatibles con otros bloques deben resaltarse visualmente (ej. mediante un cambio de color o una superposición gráfica en el punto de snap) para guiar al usuario hacia una unión correcta. 
		\item \textbf{Retroalimentación ante conexiones inválidas:}  Si el usuario intenta realizar una conexión entre bloques incompatibles, el sistema debería, en la medida de lo posible, indicar visualmente que la conexión no es permitida. \hfill 
		\item \textbf{Indicación de ejecución:} El bloque que se está ejecutando actualmente debe ser visualmente distinguible para que el usuario pueda seguir el flujo del programa. 
	\end{itemize}
	
\end{enumerate}
